Sourcify on Arkiv

What Sourcify’s database actually is, what Arkiv actually is, and what happens when you try to put one inside the other. Nothing here is quoted from a deck: figures come from the live systems, the SDK’s own constants and the public Parquet export. Where a number is extrapolated rather than measured — the full-scale costs in §5 — it is labelled, because the difference matters.

1Two shapes of database

Sourcify runs on PostgreSQL. Arkiv is not a slower Postgres — it is a different shape of storage, and knowing which shape is what lets you tell a real blocker from a detail.

Relational, which is what Sourcify has

A relational database keeps data in tables. A table has fixed, typed columns, and every row has exactly that shape. Rows in different tables are linked by foreign keys: a row in verified_contracts holds the id of a row in compiled_contracts.

The thing that makes it powerful is the JOIN. You write one query naming several tables and the engine walks the links for you, in one round trip:

-- one question, five tables, one round trip. The engine does the walking.
SELECT cd.address, cc.version, s.content
FROM contract_deployments cd
JOIN verified_contracts vc ON vc.deployment_id = cd.id
JOIN compiled_contracts cc ON cc.id = vc.compilation_id
JOIN compiled_contracts_sources ccs ON ccs.compilation_id = cc.id
JOIN sources s ON s.source_hash = ccs.source_hash
WHERE cd.chain_id = 130 AND cd.address = '\x61d6…'
ORDER BY vc.created_at DESC LIMIT 50;

SQL also gives you ORDER BY, COUNT, GROUP BY, and transactions that either fully happen or fully do not. All of it is one server you own and pay for.

Arkiv, which is a key–value store with searchable labels

Arkiv has no tables. It has entities. One entity is:

  • a key — the address of the record,
  • a payload — arbitrary bytes, up to 128 KiB, opaque to the database,
  • up to 32 typed attributes — the searchable labels,
  • an owner — a cryptographic address, not a database role,
  • an expiry — entities die unless somebody extends them.

The closest familiar thing is an object store where the tags are genuinely queryable: the payload is a blob the database will hand back but never look inside, and the attributes are the only part it can search on. Two entities need not have the same attributes at all.

You query by naming predicates over attributes. There is no JOIN: if a record points at another record, you follow the pointer with a second query.

// the same lookup against Arkiv — predicates over attributes, then follow the ref
await arkiv.select({ payload: true })
  .where(eq("ds", "sourcify"), eq("kind", "verified_contract"),
         eq("chainId", 130n), eq("address", "0x61d6…"))
  .limit(50).fetch()
// sources are NOT in here. A second fetch, by content hash, off-chain. See §5.

The one sentence to carry into the room. Postgres is a query engine that also stores things; Arkiv is a store that also answers filters. Every red cell above is a job that moves out of the database and into an adapter in front of it.

And two of those jobs the adapter cannot actually do. Ordering and counting are not relocatable: to answer GET /v2/contracts/{chain}?sort=desc&limit=50 over 44 M records with 200-per-page unordered reads, an adapter has to pull every page and sort in memory. That is not moved, that is broken — see §7 ask 1. The honest reading of the table is that the point lookup relocates cleanly and the listing path does not.

What an entity costs to write, measured

Encoding real batches locally gives the cost model exactly. It is not proportional to the data — there is a floor, and attributes are the expensive part:

calldata bytes  ≈  996  +  192 × (attributes − 1)  +  payload
shapeoverheadpayloadreading
our verified_contract, 25 attributes5,604 B~1,738 Bthe index costs 3× what the data does
a 4-byte signature, 5 attributes1,764 B86 B95% overhead

At Sourcify’s full scale the attribute overhead alone is about 249 GB of the 484 GB in §5 — more than half the backfill is the index, not the records. Every attribute is a filter you can offer and 192 bytes × 44 M you pay for it, so the attribute list is a budget, not a wish list. Trimming ours from 25 to 12 would save roughly 111 GB.

Attribute types

A typed attribute is the reason a filter can be a range and not just an equality. chainId stored as u64 supports gte; stored as text it would not.

bool i32 u64 u256 dec str addr bytes32 key

key is the interesting one: it points at another entity. That is how a foreign key survives the move — but nothing resolves it for you.

Query operators — all of them

eq ne gt gte lt lte startsWith exists hasType not and or

Twelve. That is the entire filter language. No LIKE '%x%', no regex, no ORDER BY, no COUNT. The SDK marks server-side ordering deprecated in so many words: “not supported by the network”.

4The translation: ten tables, two entity types

The tempting move is ten tables → ten entity types. It is the wrong move, because without JOIN each extra type is another network round trip on the hot path. The right question is not “how do I mirror the schema” but “what does one lookup need to answer in one query”.

5The size wall — why the split is not a preference

Measured over real Unichain contracts pulled live from sourcify.dev on 19 Aug 2026. The bar is MAX_PAYLOAD_BYTES = 131,072.

minimal lookup response — what 70% of traffic asks for192 B
our index payload: ABI + compilation + deployment10,130 B
metadata alone32,295 B
sources alone306,979 B — 2.3× over
fields=all, the complete record958,252 B — 7.3× over

Medians over 12 sampled Unichain contracts; the largest in the sample was 2,448,070 B. Across the full 2,801-contract index actually built, the largest payload written is 62,952 B — 48% of the limit.

So “keep the sources in Arkiv too” is not a design debate that a preference settles. A median contract’s source bundle does not fit in an entity, and the largest is nineteen times over. Even if the limit were lifted, the second wall arrives immediately: calldata costs 16 gas per byte and a Cheesecake block holds 36,000,000 gas, so one 958 KB record is 42% of an entire block.

That p50 is smaller than the 10,130 B in the bar chart above and the two are not in conflict: the bar is Sourcify’s raw API JSON for 12 sampled contracts, this is the compacted payload we actually write, across all 2,801. What the blob tier should be

Ranked, honestly:

  1. Content-addressed object storage + CDN. Sourcify already runs this — 242 GiB of Parquet for about $5/month.
  2. IPFS as the open mirror. Already pinned via Filebase.
  3. A decentralised blob layer (Walrus, Filecoin). The genuinely undecided option, and the one worth discussing.
  4. Not Arkiv — a source bundle is fetched by hash and never filtered on. Paying an index to hold it buys nothing.
  5. Not Postgres — that is the status quo generating the egress bill.

The hash is what makes this tier swappable later. If someone calls it “just a cache”: a cache is keyed by location, this is keyed by content.

And at Sourcify’s real scale, which is the number that matters

The POC covers 0.006% of Sourcify’s verified contracts, or 0.008% of the contracts-plus-compilations set the extrapolation below actually spans. Extrapolating the measured per-record cost linearly to all 44,391,604 verified contracts and 5,716,510 compilations — and the linearity is the assumption worth naming, because Unichain is a young, DeFi-heavy chain whose contracts are probably larger than the global median, which would make these figures an over-estimate. The entity-count side is not extrapolated: those two totals are the real row counts from Sourcify’s own export:

Unichain (measured)all of Sourcify (extrapolated)
records3,92850,108,114

Five days of a chain doing nothing but this, which is a floor rather than a schedule: at a realistic 10% share of block space it is fifty days, and at 1% it is over a year. And that is only the initial backfill. Three more things the POC’s 30 seconds does not show:

  • 7 wei is a devnet price. Every GLM figure here is a devnet artefact and should be re-derived against a real fee market before it is used in any argument.
  • The headline is the un-optimised number. Moving the ABI to the blob tier, as the card below argues, takes the backfill from ~484 GB to ~102 GB — the same five days becomes roughly a day. Quoting the larger figure is deliberate, because it is what the design as built costs, but it should not be read as the floor.
  • Entities expire, and renewal was measured, not guessed. Extending 50 real entities cost 500,000 gas — 10,000 gas each, 225 bytes of calldata. An earlier draft of this page asserted ~2,000 and a reviewer was right to call that inconsistent with the create cost in §3. At the two-month lifetime these were written with, 50 M entities need about six renewals a year each: 3.05 trillion gas a year, roughly 47 hours a year of full block utilisation, forever, paid by a funded always-on process that holds the owning key. Doubling the lifetime halves the number; it does not remove the standing obligation. This is cost of ownership, not cost of one write.

The lever nobody has pulled yet: the ABI.

The median ABI is 8,113 B of a 10,130 B index payload — 80% of everything we write. Move it to the content-addressed tier alongside sources and the whole backfill drops to roughly 102 GB, about 4.5× smaller. Keeping the ABI inline is a product choice (wallets want it in one round trip), not a requirement. It is the single biggest dial on this page and it deserves a decision rather than a default.

6What the POC actually does

Deliberately narrow, so that everything claimed is real rather than mocked.

In scope — real

  • One complete chain. Unichain (130), all 2,801 verified contracts — every one, not a sample.
  • Real Sourcify data, pulled from the live v2 API.
  • Real writes to the Cheesecake devnet, batched.
  • GET /v2/contract/{chain}/{address} served from Arkiv, with the fields / omit projection Sourcify offers.
  • A live parity diff against sourcify.dev, field by field, that is allowed to fail.
  • Queries Sourcify cannot answer — the actual argument for the move.
  • The 4-byte signature service, on its own toggle. It turned out to be the easiest thing here to move, not the hardest — see below.
  • A two-month lifetime on every entity, chosen rather than defaulted.

Out of scope — and why

  • Compiling and matching bytecode. That is Sourcify’s verifier and it is not the thing under question. The question is whether Arkiv can be the database behind it.
  • Sources and stdJsonOutput on-chain. They do not fit. §5.
  • Write path POST /v2/verify. The migration plan is dual-write behind the existing verifier, not a replacement of it.

The 4-byte service was mis-scoped, and it is the best fit on this page

It was called “a separate service” and set aside. That was wrong. Selector resolution is a pure key-value lookup with a tiny value, which is exactly the shape this database is good at — one equality on an indexed attribute, one round trip, no join, no ordering, no aggregation. Derived locally from the ABIs already fetched, so these are measured and not estimated:

distinct selectors across our 2,801 contracts12,674
payload per selectorp50 86 B · max 255 B
real 4-byte collisions (one selector, several texts)2 (0.02%)
Sourcify’s whole 9,920,797-row dictionary, grouped by selector~1.0 GB of payload

One gigabyte against the 484 GB the contract index needs. If the goal is “offer Sourcify everything Sourcify offers”, this is the cheapest yard on the field and it serves roughly 7 M requests a day.

Permanence is in scope now, with a number attached

Entities are written with a two-month lifetime. That does not make them permanent — it makes the renewal a scheduled, funded operation instead of an unanswered question. What still has no answer is who holds the key that does the extending, which is §8, not a demo setting.

The honest summary for the room.

The point lookup — the dominant read path, though Sourcify has not published a request breakdown and this document should not pretend otherwise — works on Arkiv today and answers filters the current API cannot. The listing path does not work, and the blocker is ordering, not size or money. Permanence, key custody and atomic ingest are decisions no demo can settle.

And the framing matters more than any of it. Pitched as a replacement for the transactional registry, this loses: the queries Sourcify’s own consumers depend on (sort=desc, paginated listings, COUNT for the stats page) are precisely the ones Arkiv cannot serve, while the filters we add are ones nobody is currently asking for. Pitched as a queryable, verifiable mirror — the layer people go to BigQuery, Dune and the Parquet export for — the same evidence reads as a strong fit. Same POC, and only one of those two conversations survives contact with the person who operates the database.

8Service by service — what survives the move

Sourcify is not one program. Its repository ships exactly four services, and they do not face the same way: two of them barely read the database at all. Sorting the question by service rather than by feature is what makes the answer honest.

What it is actually for here is narrow and concrete: the counts on stats.sourcify.dev, per chain and per day. Not analytics for their own sake — the public number that says how big the registry is.

The interesting part is that Postgres does not compute this live either. Sourcify already maintains a materialised view for its signature stats, because counting tens of millions of rows on every page-load is a bad idea in any database. So the ask is not “put GROUP BY in the chain”. It is: a COUNT over a predicate in the query path for the cheap cases, and for everything else the aggregate belongs in the indexer that already runs beside the network — the same shape Sourcify already chose. Asking a chain to do OLAP is asking for the wrong thing.

9Against BigQuery, specifically

This is the comparison that decides whether any of this is worth doing, because Sourcify already solved “make the database publicly queryable” — and Postgres was never the thing they solved it with.

From Argot’s own roadmap, filed under milestones completed:

“Public Queriable DB Instance: Now mirroring the Sourcify database in BigQuery (listed in Google web3 datasets). Can be plugged into Colab Python notebooks, or queried through GCP services. Also shipped an AI Playground to ask LLMs questions about the dataset.”

Worth being precise: there are two public mirrors, not one. The Parquet export on Google Cloud Storage is the bulk copy, and the BigQuery instance above is the queryable one. This section is about the second; the first is a file drop and Arkiv does not compete with it.

So the target is not their Postgres. It is a mirror — the copy that exists so outsiders can ask questions. They wanted a public queryable instance for an open public good and answered it with the most centralised option available. That is the conversation worth having, and it is a different one from “replace your database”.

Same question, different shape of answer

A query against BigQuery returns rows you designed — the columns you selected, ordered how you asked, aggregated if you wanted. A query against Arkiv returns whole records you filtered: every attribute and the payload, up to 200 at a time, in no particular order. Neither is a subset of the other.

What Arkiv actually adds

  • Verifiability, and precisely stated. Every record carries an owner address that signed it, so “is this really from Sourcify?” is a check rather than an assumption. The honest version of this claim is narrower than it first looks: BigQuery could carry signatures — a signature column, or signed snapshot roots, would work fine. Two things still differ. The protocol enforces authorship at write time, so nobody can write a record owned by Sourcify’s address without Sourcify’s key; and the reader verifies the record they actually received rather than trusting that the server returned the row that was signed. Provenance is the storage layer’s job instead of an application feature somebody has to build and keep running.
  • No gatekeeper. A public good queried through a Google account is a public good with a login. This is the argument that does not depend on any benchmark.
  • Sub-second filtered lookups at a cost per query that does not scale with corpus size, because it reads an index rather than scanning.

What it would cost them

  • The notebook and the AI Playground both break. Those are the two uses Argot names, and both are analytical: counting, grouping, free-text. Arkiv has none of it.
  • No joins means no combining verification data with anything else, which is most of what makes a public dataset interesting to a researcher.
  • So this is not a drop-in replacement for the mirror, and saying otherwise would not survive the first question.

The honest shape of the pitch. Not “leave BigQuery”. The mirror does two jobs that got bundled together because one product happened to do both: lookup and filter, and analyse. Arkiv is better than BigQuery at the first — faster, open, verifiable, no account — and cannot do the second at all. The version of this that a Sourcify engineer would say yes to is the verifiable filtered-lookup tier beside the warehouse, not instead of it. Which is a smaller claim, and the only one the evidence on this page supports.

10What this does not answer

Written after handing the document to a reviewer briefed to argue against it as Sourcify’s own engineer. These are the questions that came back, unresolved. They belong on the page rather than in a follow-up, because they are what a real operator asks first.

Ingest

There is no transaction across tiers. One verification is today an all-or-nothing write across seven Postgres tables. Here it is two entity writes plus blob puts in a different system, with no rollback. What happens when the blob lands and the entity reverts? Who retries? What happens when two verifiers race the same (chain, address)?

Dual-write is the classic trap. “Postgres stays canonical, we mirror to Arkiv” sounds free until the two disagree and there is no two-phase commit to appeal to. The parity endpoint in the POC is a detector for exactly this, not a solution to it.

History

Keying one entity per (chain, address) collapses re-verifications — 187 of them on Unichain alone, and about 42% of sourcify_matches rows across the export. Postgres keeps that history. Is a re-verification an overwrite, or a new version? Explorers that want “what did this look like before” get a worse answer than they have now, and nothing in this design has decided which it should be.

Who holds the key

Entities survive only while someone extends them, and only the owner can. If Sourcify holds that key, one compromise rewrites the public verification registry. If it is distributed, a lost key silently deletes verified contracts when the lifetime runs out. Neither is a demo problem and the POC chose two months deliberately, which sets the renewal cadence but decides nothing about custody.

Two tiers, one dangling reference

The entity holds a hash; the bytes live elsewhere with a different lifetime. If the blob is garbage-collected the entity points at nothing; if the entity expires the blob is orphaned. Who runs the reconciler, and what does a consumer see in the window where the two disagree?

Reads as a public good

Sourcify is queried without an API key by every explorer, wallet and bot on the network. Anonymous reads here are metered at 50 per hour per IP — one page-load of the POC exhausts it. Serving Sourcify’s read pattern means either an economics answer or a CDN in front, and “put an API key on the public verification registry” is not an answer anyone will accept.

Schema evolution

Postgres migrates a schema; Arkiv has none to migrate. Adding attribute 26 across 50 M already-written entities means rewriting them, at the gas in §5. Free-form storage makes the first write easy and the fifth change expensive, which is the opposite of the trade Postgres offers.

One scope note that is not a question but an omission. compiled_contracts_signatures holds 175,489,918 rows — four times verified_contracts, the largest table in the export.
