Sourcify × Arkiv  ·  How your data lives in Arkiv  ·  design draft

Not a database copy — a queryable index.

Sourcify's ~11M verified contracts, made decentralized and queryable on Arkiv, without losing the Sourcify v2 API that Foundry / Hardhat / Remix already speak. Here's the concrete shape.

Principle: don't mirror the Postgres row-for-row. Arkiv holds a queryable index + content-addressed blob refs + a renewable cold pointer. "Move the whole DB into entities" is the trap — it breaks on TTL, ordering, ownership, and large blobs.

The pattern — three pieces

Queryable index
One entity per verified contract, with indexed attributes for the real lookups (by chain+address, code hash, compiler, match).
Content-addressed blobs
Source bundles (100KB–1MB+) stay in Sourcify IPFS/GCS — Arkiv stores the hash + ref. Sourcify already keccak-addresses sources → natural fit.
Renewable cold pointer
Rarely-used records drop to a tiny pointer; the data is fetched by Arkiv tx hash. Cheaper — but still needs renewal (no permanence primitive yet).

Architecture — tooling doesn't change

Foundry · Hardhat · Remix
verify (POST std-JSON) + lookup (GET /v2/contract) — unchanged
→
Sourcify v2 API adapter
field projection · pagination/sort · owner+hash auth · TTL renewal
→
Arkiv
queryable index + cold store · blobs on IPFS/FileDB

Entities

◆ verified_contract
Hot index. Key sourcify:vc:v1:<chainId>:<addr>. Indexed attrs + compact payload (hashes+refs). TTL 30–90d, renewed on hits.
◆ cold_pointer
Tiny, always-renewed. Points to coldTxHash; data via eth_getTransactionByHash. The §4 cold tier.
◆ proxy_snapshot
Short TTL. Sourcify resolves proxies on-read → kept separate so the immutable record never goes stale.

Migration — no big bang

Dual-write
Every new verification also writes its Arkiv entity. Postgres stays canonical — zero risk.
Backfill
Stream ~11M from the Parquet export → batch-write to Arkiv. ~11k txs, ~0.1–0.3 GLM (testnet), hours. Idempotent.
Shadow-read
Serve from Arkiv but cross-check a % against Sourcify — compare hashes, measure parity + latency.
Cutover
Flip to Arkiv-first once parity + SLA hold. Full off-BigQuery only after mainnet + permanence + ownership.

What still needs product answers (→ Marcos)

Q1EOA ownership. One EOA owning ~11M public-good records is a blocker — needs multisig/threshold (no contract-signature path today).
Q2Permanence. Mandatory TTL, no permanence primitive → the renewable-index design works, but is it the blessed path?
Q3Economics. Gas for 11M writes is cheap; ongoing TTL renewals + mainnet fee spec (draft) — who pays for a public good?
Q5Ordering. No reliable server ORDER BY → listings sort client-side in the adapter. Confirm on the new testnet.
