Accuracy review of the strategy doc

13 claims checked against primary sources

The doc holds up well. Every size figure, the 4.07× vs 5.5× explanation, the egress revision, the "don't migrate" conclusion and — importantly — the warning that 15M requests/day must never be quoted as contract lookups are all confirmed against primary sources. What follows is only what needs changing, ordered by how much it would cost us if said out loud on Monday.

F1 The growth rate is overstated by roughly 7×. This is the one that must be fixed before Monday. fix

The doc states growth is "now around 189 GiB per month", sourced to issue #2866. The issue does say that. But three independent size readings disagree:

pg_database_size was 939.9 GB on 7 Aug (Kaan's own summary), 942.28 GB on 10 Aug (the doc), and 949.62 GB today. That is +9.05 GiB in 11 days = ~24.7 GiB/month.

At the observed 25.5 KiB per verification, sustaining 189 GiB/month would require 259,000 verifications/day. The measured organic rate is 33,878/day.

The explanation is in the same issue: "the tall spikes are Jul 16–17, which is when similarity-import ran." Our own curve shows 2026-07-17: +2,774,661 contracts in a single day. The 189 GiB figure was measured across a window containing a one-time bulk backfill. It is a backfill rate, not a growth rate.

Why it matters: 189 GiB/month sizes an Arkiv proposal at roughly 7× the real thing, and Kaan will know his own steady state. Quoting it makes us look like we read one issue instead of measuring.

F2 The #2866 numbers are an AI analysis of Sourcify's infra, already partially corrected — not an audited review. reframe

The doc calls it "Sourcify's own hosted Postgres cost review". The thread opens with Marco Castignoli writing: "Pasting here the tldr of the analysis done by Claude on our Infra." Kaan then pushed back on the egress figure and it was revised from 15.9 TB to 13.6 TB.

The doc already handles the egress revision correctly. Extend the same caution to the rest: cite these as Sourcify's working estimates. If we present them as audited facts and one is wrong in the room, we own the error.

F3 The 27% gap is arithmetic, not a category. We cannot claim it is "derived and operational data". sharpen

Confirmed in the exporter source: per-table figures come from pg_total_relation_size(), the total from pg_database_size(). The gap is therefore everything the ten tables are not — other tables, system catalogues, and free space and bloat inside the database.

The doc's own instinct is right ("what else sits in there is a good question for Sourcify"), but the sentence before it asserts a composition we cannot derive. Ask, do not assert — a database that has been updated in place for years can carry a lot of bloat, and if a meaningful slice of 256 GB is dead space that changes the story in Sourcify's favour, not ours.

F4 Missing: the 139 GB of duplicated metadata their own schema cannot fix. This is the strongest opening we have. add

Issue #2924, opened 10 Aug 2026 and still open: compiler metadata is stored per deployment instead of per compilation, averaging 8.5 copies. sourcify_matches is 182 GB of which 163 GB (90%) is that metadata. Normalising would free ~139 GB and shrink the table to ~19 GB.

The reason it has not been fixed is the interesting part: the Verifier Alliance schema, which they share with Blockscout and Routescan, has no slot for it. They are carrying 139 GB of duplication because a shared relational schema cannot express the relationship.

That is a content-addressed storage problem described in their own words, in their own issue tracker, opened eight days ago. It belongs in the Monday conversation.

F5 Missing: they hand-built a bytecode-prefix index last week. Arkiv has prefix search as a primitive. add

Similarity verification searches by the first 75 bytes of runtime bytecode — the rule the doc already cites. What the doc does not have is that the naive implementation walked 142k rows and took 36 seconds in production, and that in August they shipped a materialised runtime-code-prefix table (issue #2918) maintained by an insert trigger, purely to make that query fast.

Arkiv's typed query language ships STARTSWITH on typed attributes. This is the one place where a capability we already have maps one-to-one onto a problem they solved last week by hand. Worth raising as a question — "would you rather not maintain that trigger?" — not as a claim.

F6 The Parquet export is an append-only log, not a snapshot. It cannot be replayed as a backfill. fix

The doc treats the export as "the full history, every verified contract since day one". Mostly true, with a sharp edge. Files are named by an export row counter and, per the v2 design, a full file is never touched again. So the counter drifts above the live table as rows are deleted or replaced.

Measured: the file ranges imply 74.2M rows for sourcify_matches, while Sourcify measured 42.7M in that table on 10 Aug. compiled_contracts: 5.72M implied vs 5.16M measured.

Consequence for us: a migration that replays the export will write tens of millions of superseded entities unless it de-duplicates by primary key first. It also means we must not quote file-range figures as row counts — that is why this page quotes bytes per table, and takes row counts only from Sourcify's own measurements. Why the drift is that large is a genuine question for Kaan.

F7 The cheapest alternative to anything we propose is Sourcify turning their CDN on. know this

From the same issue: Cloud CDN is switched off while 88.6% of successful GETs are repeat URLs, costing about $700/month in uncached internet egress.

Any serving-layer pitch has to beat a change that costs them one afternoon. That does not kill the pitch — a CDN does not make the data queryable, verifiable or independently hostable — but if we do not raise it ourselves, someone in that room will.

F8 Kaan's own summary attributes 15M requests/day to the contract API. The doc is right and his doc is loose. confirmed

The 2025 recap says "our APIs serve over 15 Million requests per day (all Sourcify APIs)" and separately that 4byte alone serves over 7M. Kaan's summary document says sourcify.dev/server "serves ~15M requests a day", which reads as the contract API alone.

The doc's warning — never quote 15M as contract lookups — is correct and load-bearing: it is the difference between a 174 req/s target and an ~87 req/s one. Worth confirming with Kaan gently, as a question about the split rather than a correction.

F9 Two smaller things: an empty stub, and the headline number the doc never states. tidy

"Questions PB:" is an empty heading in the current draft. Either fill it or cut it before this circulates to Paweł.

And the doc never states how many verified contracts exist. It is the denominator under every other figure on the page — 43.78M as of today, 5× growth in twelve months. Lead the Context section with it.

The pilot worth proposing

4byte signature service

The strategy doc reaches this conclusion on its own and it is the best judgement in the document: 6% of the data carries about half the traffic. It is small, self-contained, schema-simple, extremely high volume, and it is a lookup service — which is the shape Arkiv actually serves well. Matthias has already said internally that this "would be quite interesting to start". The numbers:

Entities9.34 Msignature hash → text, 303 bytes/row
Backfill time~24 hat 107 entities/s · 11.7 h floor at block gas
Gas0.76e1281,024 gas/entity, flat regardless of batch size
Read load to serve81 req/s>7M requests/day, average — peaks unknown
The honest gate

Every number above except the last is comfortable. The pilot is entirely gated on the read path — 9.34M entities is a day of writing, and then we need to serve 81 requests per second against an endpoint that currently allows 50 per hour.

So the ask to engineering is narrow and answerable: what does the read path look like on the September testnet, and can a named design partner get a dedicated one? If the answer is no, the honest move is to propose a mirror rather than a migration, and say so before Sourcify discovers it.

The asks, in order

today → tomorrow → Monday

Today — Kaan

Sourcify · only what the public dataset structurally cannot answer
  1. What does the read mix actually look like across the API? Endpoint breakdown, cache-hit rate, peak requests/second and p99 latency. unit: req/day per endpoint · % cacheable · peak req/s · p99 ms  — a snapshot is an inventory, not a workload
  2. How much of the 949 GB is indexes rather than content? One read-only query gives ten rows. unit: pg_table_size / pg_indexes_size / pg_total_relation_size per table
  3. What lives in the 27% that is never exported — and how much of it is bloat rather than data? unit: GB per non-exported relation, plus dead-tuple estimate
  4. Of the 13.6 TB/month egress, which fields cause it? Marco's own conclusion was that a migration only pays if this drops ~95%. unit: TB/month split by endpoint and by field — sources vs bytecode vs metadata
  5. What is actually mutable? 75–80% is immutable, but sourcify_matches.metadata is updated in place and re-verifications overwrite. unit: rows updated/day vs inserted/day · deletions/month and their legal basis
  6. The 15M requests/day figure — is that all APIs combined, with 4byte roughly half? Our reading of the 2025 recap says yes; your summary reads as the contract API alone. unit: confirm the split. It is the difference between a 174 req/s and an ~87 req/s target.
  7. Why does the export's file counter run ahead of the live tables (74.2M vs 42.7M rows in sourcify_matches)? We want to know before we plan a backfill off it. unit: explanation — are superseded rows retained in the append-only files?
  8. Is the ERC-7730 registry still headed on-chain? The shipped design is EAS attestations over a mirrorable off-chain registry, which reads differently from "move it on-chain and make it permissionless". unit: a direction, not a number — this one changed since we last spoke

Deliberately not asked, because we computed them: contracts per day, total verified contracts, per-chain distribution, exact-vs-partial split, table sizes, compression ratio, reuse factor. Saying so explicitly is the point — it is what makes the other eight questions land as engineering rather than discovery.

Tomorrow — Arkiv engineering

Ask each owner one thing, not the room everything
  1. Read path. 50 req/hour/IP is a 5,800× gap against the pilot alone. What exists on the September testnet, and can a design partner get a dedicated endpoint? (Bouncer / API keys) blocker · everything else is downstream of this answer
  2. Query language. Is STARTSWITH index-backed or a scan at 40M entities? Are != and server-side ordering scheduled? (core protocol) ordering is marked TBD internally — we need a yes/no before Monday
  3. Ownership. Contract-account or multisig ownership that can still update, delete and extend. An EF-funded non-profit cannot put a public good behind one EOA. this is a governance blocker, not a technical preference
  4. Payload ceiling. Hard per-entity limit and the chunking boundary above it. Their compilations average ~19 KB.
  5. Data survival. Does September testnet data survive to mainnet? Sourcify has to be told this before they invest, not after. nothing has migrated between networks so far — Braga, Zeppelin, FLAN all gone
  6. Read latency under load. The soak sampled reads once a minute. We need concurrent-read numbers before we promise anything.
